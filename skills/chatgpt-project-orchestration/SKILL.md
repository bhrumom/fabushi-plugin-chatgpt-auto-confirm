# ChatGPT project orchestration

把 ChatGPT 当作规划与验收权威，把当前 agent 或插件运行时当作编排器。这个
skill 只定义项目组协议；实际的内置 Browser 或 ChatGPT 控制器由调用方提供，但
必须满足下面的 Chat surface contract。

本 Skill 是控制平面契约，不会因为写入 `SKILL.md` 就凭空提供标签页注册表、视频
录制、trace、证据摘要、精确 PR/head 自动审查或发布流水线。调用方没有这些运行时能力时，
必须把它们列为独立原子任务并停在相应门禁，不得把文档存在误报成运行时已经实现。

## 先建立可恢复的项目上下文

1. 从 GitHub `main` 读取项目登记表，找到匹配的项目 ID、项目 key、
   `PROJECT.yaml` 和 `SOURCE_OF_TRUTH.md`。复用现有项目，不因新会话、新分支
   或新 PR 创建重复项目。
2. 读取该项目的章程、范围、需求、架构、质量、发布、安全、路线图、WBS、验收
   矩阵、风险/阻塞、状态、变更日志、开放行动项和相关 ADR。若用户最新要求尚未
   落盘，先执行 secret/redaction gate，只把脱敏后的 canonical requirement snapshot
   保存到项目 `source/`，再让任何项目组据此工作；原始要求不得直接进入仓库。
3. 在实质实现前完成开源优先调查，记录候选仓库、固定审查版本、许可证、借鉴点、
   复用/改写/拒绝决定；不得把对话记忆当作调查证据。
4. 每个阶段都必须更新项目目录中的对应记录，至少包括任务记录、WBS、验收矩阵、
   状态报告和证据索引。聊天内容只是控制视图，不是最终事实源。
5. 发布前必须确认 `main` 的保护规则可由 GitHub 事实验证，并定义插件、运行时、
   tag 和构件的版本映射；不能假设空的 ruleset 查询等于分支已受保护。

## 建立五个项目组

为每个项目组创建且只保留一个 ChatGPT 浏览器标签页：

| 项目组 | 责任 | 主要落盘位置 |
|---|---|---|
| 架构组 | 阅读现状和开源资料，形成目标架构、依赖、风险，并拆成可独立验收的原子任务 | `docs/03-架构与实现策略.md`、`management/01-WBS原子任务.md`、`management/tasks/`、`decisions/` |
| 执行组 | 每个会话只负责一个原子任务，读取指定任务文件，修改实现，验证并提交分支/PR | 原子任务记录、代码、`management/05-状态报告.md`、`evidence/` |
| 代码审查组 | 针对精确 PR/head 检查实现、测试、边界和记录；问题退回执行组 | 审查记录、任务状态、审查证据 |
| 测试发布组 | 推动保护分支合并，在精确 `main` SHA 上打包并运行模拟用户 E2E，保留全量证据 | `evidence/`、发布/回滚记录、验收矩阵、状态报告 |
| 正式发布组 | 只在代码审查、测试验收和视频验收全部通过后发布正式版本 | Release、`evidence/`、发布记录、变更日志 |

“一个标签页”是项目组的浏览器传输边界，不是会话边界：执行组可以在自己的
唯一标签页中为不同原子任务创建独立的新 Chat，并行工作；上下文续接也在同一
标签页内完成。不要为每个会话打开新标签页，发现重复标签页时先确认其状态并关闭
重复项，不要关闭仍在生成的有效会话。如果当前控制器的槽位或默认策略会破坏这一
规则，返回阻塞并要求编排器调整，不要静默增加标签页。

## Chat surface contract（硬性规则）

- 使用 ChatGPT 的 **聊天/Chat** 模式，绝不使用 **工作/Work** 模式。发送前后都
  验证实际输入框、模型控件和 Chat 侧栏属于 Chat surface；模式文字变化本身不算
  切换成功。
- 复杂任务选择 `GPT-5.6 Sol` 和 `Extra High`（`xhigh`）推理；模型或档位不可用
  时报告阻塞，不悄悄降级为 Work 或未经批准的低档位。
- 每次发送都带上项目 ID、任务 ID、当前阶段、仓库路径、要读取/写入的确切文件、
  验收标准和要求的落盘记录。发送验证必须确认消息气泡确实出现，不以点击按钮或
  按 Enter 作为成功依据。
- 发送后持续观察生成状态。只要页面上仍有针对本次回答的“停止回答/Stop answering/停止生成”等可访问性按钮，就不得读取最终回答、发送下一条消息、创建新 Chat、
  切换会话/项目组或关闭标签页。只有该控件消失、消息内容稳定且页面仍在 Chat surface
  时，才可接受回答并继续；控件消失前的超时只能记为等待/失败，不能记为完成。
- 上下文过长、页面需要压缩或会话异常时，先保留旧 Chat 的完整记录，在同一项目组
  标签页中新建 Chat；把项目目录中的持久化摘要、未完成任务、已完成提交和下一步
  路径作为唯一续接输入。不要复制猜测性的上下文，也不要开新标签页。
- 只扫描并确认预期的 ChatGPT 授权卡；页面或登录状态不确定时不得点击任意按钮，
  不得在任务记录、提示词、日志或证据中写入凭证、Cookie 或令牌。

## 阶段推进

状态必须按以下顺序推进，任一门禁失败就停在当前状态并写明阻塞原因：

`PLANNED → EXECUTING → REVIEW → TEST_RELEASE → VIDEO_REVIEW → FORMAL_RELEASE → COMPLETE`

- 架构组只在项目文件夹中写出可执行计划和原子任务。每个原子任务必须有稳定 ID、
  单一目标、范围边界、输入/输出、依赖、文件所有权、验收标准、验证方式和回滚/风险。
- 执行组每个会话只认领一个原子任务，先读取该任务文件，再实现并更新它；不同任务
  若有文件或依赖冲突，先由架构组调整 WBS，不得互相覆盖。任务完成必须留下提交、
  PR/head、验证结果和下一步。
- 代码审查组必须检出或读取与 PR 声明完全一致的提交，检查代码、测试、记录、
  安全边界和开源来源。通过或退回都要写入审查记录；审查通过前不得合并。
- 测试发布组只接受保护分支上的精确合并 SHA。它必须在该 SHA 上使用 CI 生成可安装
  构件，并运行模拟用户旅程；截图要覆盖有意义的启动、登录、导航、搜索、消息、
  MiniApp/任务步骤，保留完整操作视频、trace、测试报告和平台日志。证据上传必须
  走 always 路径，成功和失败都保留；可行时按项目规则保留 90 天。测试“通过”同时
  需要断言通过和证据包完整；正式发布必须提升同一个已测试构件，或提供可验证的
  产物等价性证明，不能用未经 E2E 验证的重新构建物替代。
- 视频验收回到代码审查组：审查视频是否覆盖目标、真实用户动作、正确结果、版本、
  SHA、运行 ID 和时间戳。视频或关键证据不完整时退回测试发布组。
- 正式发布组只发布已通过上述门禁的精确 `main` SHA，验证版本单调、构件可追溯、
  安装/更新资产完整，并把 Release、回滚点和证据链接写回项目。

## 完成定义

只有当项目记录、代码审查、保护合并、精确 main 构建、模拟用户 E2E、完整证据、
视频审查和正式发布（若本任务要求发布）均有可核验事实时，才报告 `COMPLETE`。
否则返回 `in-progress`、`blocked` 或 `failed`，并给出唯一下一步。Fabushi 仓库
的重型构建、打包、原生/移动/E2E 测试必须在 GitHub Actions 完成；本地只做轻量读取、
差异检查和技能/文档校验。

更细的消息模板、记录字段、并行冲突规则和证据清单见
[references/orchestration-protocol.md](references/orchestration-protocol.md)。
