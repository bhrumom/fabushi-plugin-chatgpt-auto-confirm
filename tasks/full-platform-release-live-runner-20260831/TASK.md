# 工作范围与执行约束

## 目标

1. 盘点仓库真实支持的平台，发布一个统一版本号的全新正式版本。范围至少核对 Web/PWA、Android、iOS、macOS、Windows、Linux 与 Electron/原生包装；不存在或已废弃的平台必须以仓库和发行证据说明，不能虚构产物。
2. 使用用户指定的 `fabushi test` 工作区插件，对每个可运行的真实安装包执行安装后远程操控测试。
3. 让长时间 GitHub Actions 支持同一 Runner 内在线观察、修复和重跑：错误一出现即可处理，不等待整个 job 退出。
4. chatgpt-auto-confirm 必须持续驱动队列拥有的隐藏 ChatGPT 会话，发生渲染器、CDP、登录、状态或 Action 错配时自动恢复。

## 每轮必须执行

- 队列控制器、隐藏 ChatGPT 实例、状态监控和日常代码修改先在本机运行。主连接器使用用户指定的 `fabushi test` 工作区插件操作 `/Users/gloriachan/Documents/fabushi` 的现有 checkout，先检查工作树并保留用户改动；云端 PR、Actions、产物和 Release再切换 GitHub 连接器核验。
- 读取本目录全部文件和项目 Gmail 线程，检查是否有来自 `1315518325@qq.com` 的新要求。
- 检查正在运行的外部操作和已有 checkout，继续现有实现，禁止只读、只计划、只总结或重开相同工作。
- 每轮完成一个可验证的代码/工作流/测试/发布增量；若已有外部操作正在运行，则持续观察并并行完成不冲突的工作。
- 使用 `MAHAYANA_TASK_REPORT_V1` 报告真实进展。旧 revision 的报告不能完成新任务。

## 本地磁盘边界

开发机不得构建应用、运行应用/E2E/原生/完整测试、下载大型 SDK 或清理用户缓存。即使本地队列的一般规则允许本地验证，本仓库的磁盘安全规则仍优先：所有重型构建、安装、设备测试和发布验证只在 GitHub Actions Runner 内执行。开发机只允许持续对话、监控、阅读、精确编辑和轻量静态检查。

## 发布原则

- 使用单一版本来源或有自动一致性检查的版本映射；产物必须能追溯到 commit、workflow run、签名身份和 checksum/SBOM/provenance。
- 真实安装、启动、升级与回滚是门禁，不以“构建成功”替代。
- 商店或签名凭证缺失时，先完成所有不依赖该凭证的工作，再通过项目邮件精确请求人工介入。
- 不得覆盖用户改动、强推或把缓存/构建树纳入提交。
