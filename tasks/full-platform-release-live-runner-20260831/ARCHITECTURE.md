# 架构与安全要求

持续队列控制器和隐藏 ChatGPT 会话运行在本机；GitHub Actions 是它观察和调度的远端执行环境，不承载 chatgpt-auto-confirm 控制器本身。

## Runner 内在线修复循环

长任务必须由一个可恢复的 Runner 控制器管理，而不是把全部逻辑塞进一次不可观察的命令：

1. 将构建、安装、启动、远控和测试拆成有稳定 id 的阶段，并持久化状态、事件、日志位置、输入 commit 与产物 digest。
2. 子进程输出与结构化事件实时流入控制器；失败事件立即触发诊断，不使用固定 sleep 等待整个 workflow/job 结束。
3. 控制器允许已授权的队列 Chat 在当前 Runner checkout 创建小而明确的修改，先做安全预检，再只重跑失败阶段及其受影响依赖；通过后继续 DAG 剩余阶段。
4. 同一 Runner 可让已构建应用在隔离会话中运行，同时执行远控与测试。进程、端口、设备和产物具有租约、超时、取消和 finally 清理。
5. 在线修改必须保留 diff、命令、日志、重试原因和关联 id。不得把 Runner 变成无认证 shell，也不得将令牌、cookie、签名材料或用户输入写入日志/产物。
6. Runner 终止后仍可从加密持久状态、已提交分支和上传证据继续；修改必须最终回写到受审查的 Git 分支，不能只存在于临时 Runner。

## 安装后远程操控

- 复用并完善仓库中的统一设备控制/Computer Use 能力，通过 `fabushi test` 工作区插件驱动真实安装应用。
- 必须显式配对和授权、最小权限、短期凭证、传输加密、设备/应用范围限制、会话撤销、审计和敏感输入专用通道。
- Release 默认不开放调试后门。远控能力必须是正式设计的安全功能或经测试签名明确启用的能力，并对未授权、过期快照、锁屏、跨应用和重放做负向验证。
- 提供应用发现/启动/停止、语义状态树、应用范围截图、点击/滚动/键盘/文本输入、结构化运行时状态和诊断导出。坐标回退必须绑定最新快照并防止跨 UI 代际误操作。

## ChatGPT 自动确认健康对比

- 以队列拥有的隐藏 ChatGPT 实例及其当前会话为第一现场，检查真实的模型/工具活动时间线。
- 与插件的 task id、revision、round、status、next task、审计记录、Runner step 和 GitHub Actions 状态交叉核对。
- 无活动但插件声称运行、Action 已结束但插件仍等待、报告与会话不一致、renderer/CDP/login 失败均属于异常；必须保留任务 checkout/分支/邮件线程/队列状态并恢复，不得创建重复任务冒充重启。
